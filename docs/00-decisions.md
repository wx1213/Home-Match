## D-001  邀请超时淘汰范围

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：卖方 24h 未响应被淘汰后，是否从该买方的推荐列表永久移除？
- **决定**：**本轮不可见，下轮重新计算**
- **理由**：
  - 避免误杀（卖方可能是临时有事）
  - 保留撮合机会
  - 多次超时会被"降权规则"自然处理
- **替代方案**：
  - 永久移除 → 严苛，不利于生态
  - 24h 冷却期 → 折中，但实现稍复杂
- **影响**：推荐算法、邀请表淘汰状态字段语义

## D-002  信用分公式

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：信用分 = 评价均分 × 活跃系数，活跃系数具体怎么算？
- **决定**：
  ```
  基础分   = 评价均分 × 20               // 1-5 星 → 20-100 分
  活跃系数 = min(1.0, 0.3 + 0.7 × min(1, 近30天有效响应数/10))
             // 完全不活跃 → 0.3 起步
             // 近30天响应 ≥ 10 次 → 1.0 上限
  信用分   = 基础分 × 活跃系数            // 范围: 6 - 100
  ```
- **理由**：
  - 完全不活跃的人不能仅凭历史高分持续获益
  - 0.3 是地板分（避免新用户一上来分太低）
  - 10 次/月是健康独立经纪人的合理基线
- **替代方案**：
  - 直接相加（均分 + 活跃度）→ 难以权重平衡
  - 评价次数取对数 → 数学优雅但产品不好解释
- **影响**：
  - 评价表、用户表都需要"近 30 天响应数"聚合字段
  - 每日定时任务计算并缓存（避免每次实时聚合）
- **可调参数**（后续如发现不合理）：
  - `RATING_SCALE = 20`
  - `INACTIVITY_FLOOR = 0.3`
  - `ACTIVITY_TARGET = 10`（次/月）

## D-003  市场均价数据来源

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：房源"市场均价"从哪来？
- **决定**：**自建小区均价表**（`community_prices` 辅助表）
- **理由**：
  - 第三方 API（链家/贝壳）合作门槛高、合规风险大
  - MVP 阶段仅做"提示"，不强制
  - 自建可平滑演进
- **实施方案**：
  - `community_prices` 表：`(community_id, period_month, avg_price, sample_count, source)`
  - 数据来源：用户输入的"同小区历史成交"做增量
  - 偏差校验：发布时若偏离 ±30% → 标记"需核实"（仅提示，不阻止）
- **影响**：
  - 新增 `community_prices` 表 + 定时爬虫/聚合任务（**二期**实现）
  - MVP 阶段可只建空表，"市场均价校验"功能降级为"无数据时不提示"

## D-004  评价可见性

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：评价是匿名还是实名？
- **决定**：**双方互评内容对方实名可见，第三方可见脱敏**
- **理由**：
  - 合作双方需要真实反馈才有约束力
  - 第三方（未合作过的经纪人）只看到脱敏评价，避免偏见
- **脱敏规则**：
  - 第三方视图：保留评分 + 评论内容 + 时间，**隐藏**评价人姓名/头像
  - 双方互评视图：保留全部信息
- **影响**：
  - 评价 API 需要两个响应 schema（`ReviewForParty` vs `ReviewForPublic`）

## D-008  LLM 月预算

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：LLM 月预算上限？
- **决定**：
  | 阶段 | 金额 | 说明 |
  | --- | --- | --- |
  | **Soft cap（软告警）** | **¥2,000 / 月** | 累计达此值 → 邮件/微信通知管理员 |
  | **Hard cap（硬上限）** | **¥5,000 / 月** | 达此值 → 强制降级到规则匹配 |
  | **MVP 上线首月** | **建议 ¥3,000 缓冲** | 用于异常流量测试 |
- **成本估算**：
  - DeepSeek-V3：约 ¥0.001 / 1k tokens（输入）/ ¥0.002 / 1k tokens（输出）
  - 单次推荐调用约 2k 输入 + 0.5k 输出 ≈ ¥0.003
  - 月 10,000 次推荐 ≈ ¥30
  - 方案生成（每合作 1 次）：约 ¥0.1
  - 月 500 次合作 ≈ ¥50
  - 评价分析 + 链接解析 + 异常检测 ≈ ¥200/月
  - **保守总成本：¥300-500 / 月**，远低于预算
- **影响**：
  - LLM 网关层需要 token 计数 + 月度聚合
  - Sentry 集成 LLM 调用日志
  - 管理员后台需要"用量看板"（**Web 后台**模块）

## D-009  贝壳链接解析方式

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：贝壳链接走官方 API 还是自建爬虫？
- **决定**：**MVP 阶段降级为"用户手动复制粘贴"**，自建爬虫/官方 API 暂不实现
- **理由**：
  - 贝壳找房有反爬（Cloudflare、IP 黑名单、登录墙）
  - 自建爬虫法律风险高（不正当竞争、ToS 违反）
  - 官方 API 不开放
  - **MVP 阶段用户手动粘贴链接 + 提取关键字段（链接本身）即可**，等合作或合规明朗再做解析
- **降级方案**：
  - 用户粘贴链接 → 存为 `source_url` 字段
  - 表单其他字段让用户手动填
  - AI 仅做"链接真实性校验"（是否能访问、是否 404）
  - 真实字段解析放到**二期**（等评估合规渠道）
- **影响**：
  - 减少 LLM 调用（无需解析内容）
  - 用户体验略降（手动填）但可控
  - 字段提取功能保留接口位（`PropertyParseService.parse_from_url()`），但 MVP 返回 None

## D-010  实勘水印规则

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：实勘水印的具体规则？
- **决定**：
  | 项目 | 规则 |
  | --- | --- |
  | 位置 | **右下角**，距边缘 20px |
  | 主文字内容 | `{经纪人姓名} · {拍摄日期 YYYY-MM-DD} · HomeMatch` |
  | 字号 | **24px** |
  | 颜色 | **白色** |
  | 透明度 | **0.6** |
  | 字体 | **思源黑体**（开源、可商用） |
  | 全图斜纹 | **45° 斜向 tile 水印**，间距 200px，内容同主文字，**透明度 0.15** |
  | 输出格式 | JPEG 85 质量，保留原图分辨率 |
  | 处理时机 | 上传后由 RQ 异步任务处理，不阻塞上传响应 |
- **理由**：
  - 双层水印（右下角 + 斜纹）防止裁剪绕过
  - 异步处理避免用户等待
  - 思源黑体无版权风险
- **影响**：
  - 引入 `Pillow` 依赖
  - 需要中文字体文件（`SourceHanSans.otf`，约 10MB，建议放 OSS）
  - 新增 `WatermarkWorker`（RQ 任务）

## D-011  敏感字段加密

- **日期**：2026-06-04
- **状态**：✅ 已采纳（推荐）
- **问题**：敏感字段是否需要加密存储？
- **决定**：**MVP 阶段：手机号 AES-256 加密存储；身份证暂不收集（避免合规复杂度）**
- **理由**：
  - 经纪人手机号是 PII，必须加密
  - MVP 不收集身份证（合作确认环节不强制上传），降低合规复杂度
  - 加密不影响查询效率（用 `pgcrypto` 扩展或应用层 AES）
- **实施方案**：
  - 应用层 AES-256-GCM 加密手机号
  - 密钥从环境变量读取（**绝不**入库）
  - 加密后存储格式：`base64(iv) + ":" + base64(ciphertext) + ":" + base64(tag)`
  - 索引用"加密后的哈希"（HMAC-SHA256）以支持精确查询
- **二期**：
  - 如需收集身份证，加密 + 双向认证
  - 考虑接入专业 KMS（阿里云 KMS、AWS KMS）

## D-012  移动端跨端框架选型

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：iOS + Android 双端用什么技术栈？
- **决定**：**Flutter（Dart 3.x）**
- **理由**：
  - **一码双端**，MVP 阶段开发速度比 RN/原生快 1.5-2 倍
  - 官方支持 **Material Design 3**（Android）+ **Cupertino**（iOS）双风格，跨端体验都像原生
  - 国内生产案例丰富：阿里、字节、腾讯、美团、京东都有大量 Flutter APP
  - 包体积、启动速度、性能都已达生产级
  - 生态成熟：`firebase_messaging`、`cached_network_image`、`image_picker` 等主流插件齐全
  - 团队不必同时维护 Swift + Kotlin 两套代码
- **替代方案**：
  - **React Native**：团队有 React 经验可选，但 Bridge 架构有性能损耗
  - **原生（Swift + Kotlin）**：体验最好，但成本 2 倍，MVP 阶段不建议
  - **uni-app / Taro**：Web 技术栈友好，但性能/体验偏 H5，不够"主流 APP"
- **影响**：
  - 后端 API 仍为 RESTful（不受影响）
  - 推送方案统一用 `firebase_messaging` 封装（[D-014](#d-014)）
  - 图片选择/压缩/裁剪用 `image_picker` + `flutter_image_compress`
- **可调**：上线后若体验不达预期，可针对单端用 Platform Channel 写原生

## D-013  移动端认证机制

- **日期**：2026-06-04（v0.4 调整）
- **状态**：✅ 已采纳
- **问题**：APP 用什么方式登录？
- **决定**：**微信登录**为主，**Apple 登录**（iOS 上架合规要求）为必须，**手机号 + 短信**作为兜底
- **理由**（v0.4 调整原因）：
  - 独立经纪人群体 90%+ 都有微信，**点一下就登录**比收验证码再输入快得多
  - 微信能直接拿到用户头像、昵称，**首屏就有"真人感"**，留存率明显更高
  - iOS 政策：用了第三方登录就必须有 Apple 登录，**这是硬性合规要求，不是可选项**
  - 短信验证码作为**兜底**（没装微信 / 微信异常 / 老年用户备用）
- **实施方案**：
  - **主流程**：用户点"微信登录" → 微信授权 → 后端用 `code` 换 `openid` + `unionid` → 查 `users` 表 → 已有则登录，无则自动注册 → 返回 JWT
  - **iOS 强制**："通过 Apple 登录"按钮（与微信按钮并列，同等大小）
  - **短信兜底**：用户主动点"用手机号登录"才出现（不在首屏抢位置）
  - **首次登录**：未注册用户自动注册
  - **JWT 续期**：Access Token 2 小时，Refresh Token 30 天
- **替代方案**：
  - 短信为主 → 用户路径长，留存差
  - 仅微信登录 → iOS 上架被打回
  - 密码登录 → 体验差
- **影响**：
  - 微信开放平台申请移动应用（**业务侧**需公司主体+备案号，所以 MVP 阶段先用"微信开发者测试号"）
  - Apple Developer 账号（**业务侧**）
  - `users` 表字段：`wechat_unionid`（主键）、`wechat_openid`（按 app 分）、`phone_encrypted`（兜底时填）、`phone_hash`、`apple_user_id`
  - Flutter 端 `fluwx` 或 `wechat_kit` 接入
- **MVP 阶段兼容**：
  - 没拿到正式资质时，**用微信开发者测试号 + 手机号短信**双轨跑功能
  - 资质到位后切换到正式号，代码无需改动（只换 AppID）

## D-014  推送通知方案

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：邀请/方案/超时等关键事件如何实时通知用户？
- **决定**：**APNs（iOS）+ FCM（Android）**，通过 Flutter `firebase_messaging` 统一封装
- **理由**：
  - 行业标准方案
  - Flutter 端一次集成，双端生效
  - 后端用 Firebase Admin SDK 统一发送
- **实施方案**：
  - **设备注册**：APP 首次启动 / 登录后 / 切换账号后，调用 `/v1/devices/register` 上报 `fcm_token` + `platform`
  - **消息类型**：
    - **通知栏消息**（自动弹出）：紧急事件（邀请超时前 2h 提醒）
    - **数据消息**（静默）：APP 内实时刷新（合作状态变化）
  - **后端发送**：封装 `PushService`（APNs/FCM 双通道），失败重试 3 次
  - **消息幂等**：每个事件带 `event_id`，APP 端去重
- **国内 Android 厂商适配（**二期**）**：
  - 华为 / 小米 / OPPO / vivo 各有自家推送通道
  - 必要时接入"友盟推送"或"个推"做多通道聚合
  - **MVP 暂不处理**，等用户量起来再做
- **影响**：
  - 新增 `devices` 表（user_id, fcm_token, platform, app_version, last_active_at）
  - 引入 Firebase 项目（建议海外账号，国内 Android 厂商适配再单独处理）
  - 后端 `firebase-admin` 依赖

## D-015  APP 内测与发布渠道

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：开发版/内测版/正式版怎么分发？
- **决定**：
  - **iOS 内测**：**TestFlight**（Apple 官方，25 个内部测试员 + 10000 个外部测试员）
  - **Android 内测**：**Firebase App Distribution**（国外）或 **蒲公英 / fir.im**（国内，更快）
  - **iOS 正式**：**App Store**
  - **Android 正式**：**Google Play** + **国内安卓市场**（华为/小米/OPPO/vivo/应用宝）**至少 3 个**
- **理由**：
  - TestFlight 是 iOS 唯一稳定的内测渠道
  - 国内 Android 上架各厂商市场是刚需（不靠 Play Store）
  - 蒲公英/ fir.im 国内下载快，免审核
- **上架资质**（**业务侧**）：
  - iOS：Apple 开发者账号（$99/年，公司主体 D-U-N-S 编号）
  - Android 各市场：营业执照 + 软件著作权（公司主体）
  - **APP 涉及房产经纪，可能需要 ICP + 房产经纪机构备案**（具体看当地政策）
- **影响**：
  - 业务侧需提前准备各类资质（建议 MVP 上线前 1-2 个月开始申请）
  - CI/CD 流程需要对接各发布渠道

## D-016  APP 强制更新策略

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：如何保证用户使用最新版本（避免老版本 bug）？
- **决定**：**软提示（recommend）+ 硬阻断（force）双层**
- **理由**：
  - 老版本可能有关键 bug 修复或后端不兼容
  - 不能一上来就阻断，会引发用户差评
  - 给用户"更新到最新版本"的引导
- **实施方案**：
  - 后端维护 `app_versions` 表（platform, min_supported_version, latest_version, force_update, release_notes, download_url）
  - APP 启动时调用 `/v1/app/check-version`
  - **`force_update = true` 且当前 < `min_supported_version`** → 阻断式弹窗（仅"立即更新"按钮）
  - **`force_update = false` 但有 `latest_version` 更新** → 提示式弹窗（"稍后" / "立即更新"）
- **影响**：
  - 新增 `app_versions` 表
  - 启动页需要"检查更新"步骤

## D-017  图片处理（移动端）

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：手机拍照的实勘图如何处理？
- **决定**：**客户端预压缩 + 清除 EXIF + 服务端加双层水印**（与 D-010 协同）
- **理由**：
  - iOS HEIC 格式 Android 不支持，需要客户端转 JPEG
  - 手机照片 EXIF 包含 GPS/设备信息，**必须清除**（隐私）
  - 服务端水印是最后防线（防止被绕过客户端）
  - 客户端预压缩省流量
- **实施方案**：
  - **客户端**（Flutter `flutter_image_compress`）：
    - 压缩到最长边 2048px
    - 输出 JPEG 质量 85
    - 清除所有 EXIF（含 GPS、机型、时间）
  - **服务端**（Pillow + RQ）：
    - 二次加 D-010 规定的水印
    - 最终存到 OSS
  - **OSS 直传**：APP 不经过后端中转，直接用后端签发的 OSS STS Token 上传（省后端带宽）
- **影响**：
  - Flutter 端 `flutter_image_compress` 依赖
  - 服务端需新增 `/v1/upload/sign` 颁发 STS Token 接口
  - 服务端 Pillow 任务继续保留（D-010）

## D-018  离线支持范围

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：MVP 阶段是否做离线支持？
- **决定**：**MVP 只做"列表缓存 + 详情只读"**，不做完整离线
- **理由**：
  - 完整离线（写操作、冲突合并）开发成本极高
  - 房产撮合是强实时业务，离线数据价值低
  - 但弱网体验必须保证：进入 APP 后能看到上次的数据
- **实施方案**：
  - APP 端用 `Hive` 或 `Isar` 本地存最近一次请求的列表
  - 断网时显示缓存数据 + 顶部"网络已断开"提示
  - 联网后自动刷新
  - **写操作（邀请、评价、提交方案）必须联网**，离线时按钮置灰
- **影响**：
  - Flutter 端引入本地存储库
  - 网络监听（`connectivity_plus`）组件

## D-019  Deep Link / Universal Link

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：是否支持从外部链接打开 APP？
- **决定**：**MVP 基础版**：iOS Universal Link + Android App Link，支持"邀请分享链接"
- **理由**：
  - 邀请分享是高频场景（"我给你分享个合作"）
  - 链接打开 APP 直接进入合作详情，体验流畅
  - 不做就没有"主流 APP 感"
- **实施方案**：
  - 域名：`hmatch.cn`（示例）+ `/.well-known/apple-app-site-association`（iOS）+ `/.well-known/assetlinks.json`（Android）
  - URL 格式：`hmatch://invitation/{invitation_id}`（自定义 scheme 兜底）
  - 链接生成：APP 内"分享给好友"按钮 → 拼接 URL + 短链
  - **短链服务**：MVP 阶段用后端自建 `/v1/share/shorten`（映射到真实 ID）
- **影响**：
  - 域名 + SSL 证书
  - 后端短链服务
  - iOS 苹果开发者后台关联域名
  - Flutter 端 `uni_links` 库

## D-020  数据埋点与监控

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：用户行为和异常如何采集？
- **决定**：**Sentry（错误+性能）+ 自建事件日志（业务）**，**不接第三方埋点 SDK**
- **理由**：
  - Sentry 免费层够 MVP 用，错误/性能一体化
  - 第三方埋点（友盟、神策）成本高、隐私合规风险
  - 自建事件日志足够支持产品决策
- **实施方案**：
  - **Sentry**：APP 端崩溃 + 后端异常 + LLM 调用追踪
  - **业务事件日志**：
    - 关键事件：注册、发布需求、推荐生成、邀请发送、方案提交、握手、评价
    - 字段：`user_id`, `event_name`, `event_data` (JSONB), `app_version`, `platform`, `created_at`
    - 后端用 `event_logs` 表 + 异步落库（避免阻塞主流程）
  - **看板**：MVP 阶段 SQL 查询；二期接入 Metabase / Superset
- **影响**：
  - 新增 `event_logs` 表
  - Sentry Flutter SDK 集成
  - 后端事件埋点函数封装

## D-021  MVP 阶段：先功能验证，App Store 上线延后

- **日期**：2026-06-04
- **状态**：✅ 已采纳
- **问题**：公司主体 / 备案号 / 苹果开发者账号 等业务资质尚未到位，是否阻塞开发？
- **决定**：**不阻塞**。MVP 阶段用"开发模式"做功能验证，App Store / 应用市场上线推到验证后
- **理由**：
  - 业务资质申请周期长（公司注册 1-2 周 + 微信开放平台审核 1-2 周 + Apple Developer 审核 1 周 + 安卓市场审核各 1-2 周）
  - **功能验证不依赖上线资质**：iOS 用模拟器/Android 用模拟器+真机 USB 调试即可完整跑通
  - 业务资质可以在**开发进行中**并行申请，节省总时间
  - 验证通过后再上 App Store，比"匆匆上架后发现问题被打回"更好
- **"开发模式"如何做功能验证**：
  - **后端**：本地起服务 + Swagger UI（`/docs`）手测接口 + 单元测试
  - **iOS APP**：Mac 上用 iOS Simulator 跑，**完全免费**，能验证所有功能
  - **Android APP**：Android Emulator 跑，或 USB 连真机调试
  - **推送**：用 Firebase Console 测试推送（无需正式资质）
  - **微信登录**：用**微信开发者测试号**（每个微信号可注册最多 5 个测试号），手机扫码即可登录
  - **短信**：用阿里云短信**测试签名**（每天 100 条免费额度）
  - **OSS**：用阿里云 OSS **测试 Bucket**（创建后默认有测试额度）
- **资质申请清单**（**业务侧并行启动**）：
  - [ ] 公司注册（如已有可跳过）
  - [ ] ICP 备案（如域名要解析到国内）
  - [ ] 微信开放平台账号 + 移动应用申请（**最关键**，需公司主体+营业执照+对公账户验证）
  - [ ] Apple Developer 账号（$99/年，需 D-U-N-S 编号）
  - [ ] 华为/小米/OPPO/vivo 开发者账号（各平台账号 + 软件著作权）
  - [ ] 阿里云短信正式签名（需营业执照 + 业务场景说明）
  - [ ] 域名注册 + SSL 证书（如使用 `api.hmatch.cn`）
- **影响**：
  - **开发节奏不受影响**
  - 业务侧需在 1-2 周内启动资质申请
  - 资质到位后，只需修改配置（AppID、签名、Bundle ID 等），**代码无需重写**
  - 至少**节省 4-6 周**总周期
